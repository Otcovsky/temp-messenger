# Протокол Temp Messenger, версия 1

## Идентичность

При первом запуске браузер создаёт и хранит в IndexedDB (закрытые ключи неизвлекаемые):

| Ключ | Алгоритм | Назначение |
|---|---|---|
| `IK` | X25519 | ключ личности, обмен ключами |
| `SIG` | Ed25519 | подписи (зарезервирован для групп) |
| `AUTH` | Ed25519 | доступ к своим ящикам на сервере, не связан с личностью |

Если браузер не поддерживает X25519/Ed25519 в Web Crypto, используется `@noble/curves`; закрытые ключи
тогда хранятся как сырые 32 байта. Формат ключей и вычисления те же, так что такие клиенты совместимы с остальными.

## Почтовые ящики

Ящик — случайный ID, 16 байт в base64url (22 символа). Каждому собеседнику выдаётся свой ящик.
Читать ящик может только владелец `AUTH`-ключа, создавший его. Писать может любой, кто знает ID.

## Приглашение

Ссылка `https://<host>/#i=<base64url(JSON)>`. Часть после `#` на сервер не отправляется.

```json
{ "v": 1, "ik": "<IK_A>", "sk": "<SIG_A>", "e": "<E_A>", "m": "<ящик A>", "n": "Имя" }
```

`E_A` — одноразовый X25519-ключ. Принявший (B) создаёт `EK_B` и считает:

```
SK = HKDF-SHA256(ikm = 0xFF*32 || DH(IK_B, E_A) || DH(EK_B, IK_A) || DH(EK_B, E_A),
                 salt = 0*32, info = "TM-X3DH-v1", 32 байта)
AD = IK_B || IK_A
```

B запускает Double Ratchet как отправитель, `E_A` — первый ratchet-ключ A. Первое сообщение B (`hello`)
уходит в ящик A и содержит ящик B. Пока A не ответит, B прикладывает к каждому сообщению заголовок
`pk = {ik: Enc(IK_B), ek: EK_B, e: E_A}`, чтобы A мог вычислить `SK`.

Заголовок `pk` видит сервер, а `IK_B` у человека один на все чаты, поэтому он зашифрован:

```
key (32) || iv (12) = HKDF-SHA256(ikm = DH(EK_B, E_A), salt = 0*32, info = "TM-PreKey-v1")
Enc(IK_B) = AES-256-GCM(key, iv, IK_B, AD = EK_B || E_A)        48 байт
```

`EK_B` одноразовый, этим ключом шифруется одно значение, так что постоянный IV безопасен.
Если `pk.ik` — 32 байта, это открытый `IK_B` от старого клиента; он принимается как есть.

## Double Ratchet

По [спецификации Signal](https://signal.org/docs/specifications/doubleratchet/):

- `KDF_RK(rk, dh) = HKDF(salt = rk, ikm = dh, info = "TM-Ratchet") → rk' (32) || ck (32)`
- `KDF_CK(ck)`: `mk = HMAC(ck, 0x01)`, `ck' = HMAC(ck, 0x02)`
- Шифр: `HKDF(mk, info = "TM-MsgKeys") → ключ AES-256-GCM (32) || IV (12)`, AD = `AD || dh || pn || n`
- До 1000 пропущенных ключей за шаг, хранится не больше 2000.

## Слои сообщения

**1. Конверт, его видит сервер:**
```json
{ "t": "send", "id": "<id>", "to": ["<ящик>"], "payload": "<строка>", "notify": true }
```
`notify` ставится на сообщения, о которых получателю стоит показать уведомление: `true` — `hello`,
`text`, `file`; `"call"` — приглашение к звонку; `"call-end"` — звонок закончился без ответа.
У квитанций, `goodbye` и остальных сигналов звонка поля нет. См. «Пуш-уведомления».

**2. payload:**
```json
{ "v": 1, "h": { "dh": "...", "pn": 0, "n": 3 }, "ct": "<base64url>", "pk": { ... } }
```

**3. Содержимое (внутри `ct`).** JSON, дополненный до кратного 256 байт (0x80, затем нули):
```json
{ "id": "<id>", "ts": 1731312000000, "conv": "<id группы, если есть>", "type": "text", "body": { "text": "..." } }
```

| type | body | |
|---|---|---|
| `hello` | `{name, mailbox, sigPub}` | первое сообщение по приглашению |
| `text` | `{text}` | |
| `file` | `{blob, key, size, name, mime, caption?, album?}` | файл с необязательной подписью, см. «Файлы» |
| `receipt` | `{status: "delivered" \| "read", ids: [...]}` | квитанции |
| `goodbye` | `{}` | собеседник удалил чат |
| `call-offer` | `{call, sdp}` | приглашение к звонку, см. «Звонки» |
| `call-answer` | `{call, sdp}` | ответ на звонок |
| `call-ice` | `{call, candidates: [...]}` | адреса для соединения, найденные позже |
| `call-end` | `{call, reason}` | звонок закончен или отклонён |

Неизвестные типы игнорируются. Планируются: `group-*`, `sender-key`, `edit`, `delete`, `reaction`.

## Файлы

Файл передаётся отдельно от сообщения: размер сообщения ограничен 64 КБ.

1. Отправитель создаёт случайный ключ `K` (32 байта) и id файла (16 байт, base64url).
2. Дополняет файл по схеме [Padmé](https://lbarman.ch/blog/padme/) (0x80, затем нули) и шифрует:
   ```
   ct = AES-256-GCM(K, iv = 0*12, padded, AD = "TM-File-v1")
   ```
   Ключ одноразовый, поэтому нулевой IV безопасен, а шифротекст для того же `K` всегда одинаковый —
   повторная загрузка после сбоя отдаёт серверу те же байты.
3. Загружает `ct` на сервер (`PUT /blob/<id>`), затем отправляет обычное сообщение `file`:
   ```json
   { "type": "file", "body": { "blob": "<id>", "key": "<K>", "size": 70000, "name": "отчёт.pdf", "mime": "application/pdf", "caption": "Итоги за ноябрь" } }
   ```
   `caption` — подпись к файлу (как текст обычного сообщения, до той же длины). Без подписи поля нет;
   клиенты, которые о нём не знают, просто показывают файл.

   Несколько файлов, отправленных одной пачкой, — это отдельные сообщения `file` (у каждого свой
   ключ и id на сервере) с общим `album` — случайным id из 16 байт base64url. Получатель собирает их
   в один пузырь в порядке `ts`. Подпись — только у последнего файла пачки, так что клиент без
   поддержки альбомов покажет её под всеми файлами. У одиночного файла поля `album` нет.
4. Получатель скачивает `ct` (`GET /blob/<id>`), расшифровывает, сверяет размер и сообщает серверу,
   что файл скачан (`POST /blob/<id>/done`).

Сервер видит только id, примерный размер и ключ доступа загрузившего (для квоты); имя, тип и ключ
файла — внутри зашифрованного сообщения. Файл стирается, когда его скачали все `n` получателей,
или через 7 дней. Для группы файл загружается один раз с `n` = числу участников, а ключ рассылается
каждому в его сообщении.

```
PUT  /blob/<id>?n=<получателей>   X-TM-Auth: <AUTH pub>.<sig>      тело — ct
     sig = Ed25519(AUTH, "tm-blob-v1:<id>:<длина ct>:<n>")
     201 — сохранён, 200 — уже был (повтор), 403 — подпись, 409 — id занят,
     413 — больше 26 МиБ, 507 — кончилась квота
GET  /blob/<id>                   200 — ct, 404 — нет (истёк или все скачали)
POST /blob/<id>/done              204
```

Клиент отправляет файлы до 25 МиБ. Квоты сервера: 256 МиБ на ключ доступа, 2 ГиБ всего
(переменные `TM_MAX_BLOB_BYTES`, `TM_BLOB_QUOTA_PER_OWNER`, `TM_BLOB_QUOTA_TOTAL`, `TM_BLOB_TTL_SEC`).

## WebSocket `/ws`

```
← challenge {nonce}
→ auth {pub, sig}                 sig = Ed25519(AUTH, "tm-auth-v1:" || nonce)
← ready {push?}                   push — открытый ключ VAPID, если сервер шлёт пуш-уведомления
→ register {mailbox, invite?}     ← registered {mailbox, created}, затем msg из очереди
                                  invite: true — ящик ждёт ответа на приглашение, false — обычный
→ probe {mailbox}                 ← probe {mailbox, state: "open" | "used" | "none"}
→ unregister {mailbox}            ← unregistered {mailbox}
→ send {id, to:[...], payload, notify?, ttl?}  ← sent {id, failed:[{to, reason}]}
                                  ttl — сколько секунд хранить недоставленное (не больше 7 дней)
→ ice                             ← ice {servers, ttl}       STUN/TURN для звонка, см. «Звонки»
→ push-sub {endpoint, p256dh?, auth?}  ← push-sub {ok: true} подписка этого ключа AUTH, одна;
                                                             p256dh и auth — её ключи (для пометки «звонок»)
→ push-unsub                      ← push-unsub {ok: true}
→ push-test {kind?}               ← push-test {status}       пробный пуш себе (kind: "call" — как о звонке); status — HTTP-ответ
                                                             пуш-сервиса, 0 — до него не достучались
← msg {id, mailbox, payload, ts}
→ ack {mailbox, ids:[...]}        сервер удаляет сообщения
→ ping                            ← pong
← error {code, ref?}                ref — id сообщения (send) или ящик (register, probe, unregister, ack)
```

Перед принятием приглашения клиент спрашивает `probe`: чат создаётся, только если `state = "open"`.
`used` — по ссылке уже подключились (пригласивший перерегистрировал ящик с `invite: false`),
`none` — приглашение отозвано, чат удалён или ящик истёк.

Клиент шлёт `ack`, только когда сообщение и новое состояние храповика записаны в базу одной
транзакцией (или сообщение негодное и отброшено). При сбое записи `ack` не уходит, и сервер
пришлёт сообщение снова при следующей регистрации ящика.

Если сервер ответил на `send` отказом `no_mailbox`, собеседник помечается недоступным. Пометка
снимается, когда от него приходит новое сообщение: ящик мог истечь, пока человек был не в сети.
После `goodbye` пометка окончательная.

Сервер отбрасывает дубликаты по паре (ящик, id), поэтому повторная отправка безопасна.
Недоставленные сообщения хранятся 7 дней, ящик без подключений — 30 дней.

## Пуш-уведомления

Нужны, чтобы человек узнал о сообщении, когда приложение закрыто. Выключены, пока пользователь сам
не включит их в настройках.

1. Сервер при первом запуске создаёт ключ VAPID (P-256, хранится в базе) и отдаёт открытую часть в `ready`.
2. Клиент подписывается у пуш-сервиса своего браузера (`pushManager.subscribe` с этим ключом) и шлёт
   серверу адрес подписки: `push-sub {endpoint}`. Подписка привязана к ключу `AUTH`, то есть к браузеру,
   а не к ящику. Клиент повторяет `push-sub` при каждом подключении.
3. Когда в ящик ложится сообщение с `notify: true`, сервер ждёт `ack`: 0,3 с, если у ящика нет открытого
   соединения, и 2 с, если есть (соединение уснувшего телефона выглядит открытым). Если сообщение так и
   не забрали, владельцу ящика уходит пуш. Пачка сообщений за время ожидания даёт один пуш.
4. Пуш о сообщении — пустой запрос `POST <endpoint>` с заголовками
   `Authorization: vapid t=<JWT>, k=<ключ>`, `TTL: 86400`, `Urgency: high`, `Topic: tm`.
   Тела нет, поэтому шифровать нечего.
   Пуш о звонке несёт одну пометку: `{"k":"call"}` («вам звонят», `TTL: 45`) или `{"k":"end"}`
   («звонок закончился без ответа»). Она зашифрована ключами подписки по
   [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291) (`Content-Encoding: aes128gcm`), так что
   пуш-сервис её не читает. Ни имени, ни ящика, ни id звонка в ней нет. Подписке без ключей
   (клиент прежней версии) вместо этого уходит обычный пустой пуш.
   Если свёрнутое приложение ещё работает и забрало сообщение само, пуша не будет — такое же
   уведомление оно показывает само.
5. Service worker на пустой пуш показывает одно и то же уведомление «Новое сообщение». Сообщения
   приложение забирает само, когда его откроют.
   На пометку `call` он показывает «Входящий звонок» и повторяет его каждые 3 секунды (до 8 раз)
   со звуком и вибрацией, пока приложение не откроют; на `end` — заменяет его на «Пропущенный
   звонок». Свой звук уведомлению сайт задать не может: громкость и мелодия — из настроек телефона.

Что кому становится известно:

- **Пуш-сервис** (Google, Apple, Mozilla, Microsoft) — время, когда этому браузеру пришло
  сообщение. Ни текста, ни отправителя, ни ящика в запросе нет. Пуш о звонке отличается от пуша
  о сообщении размером (у него есть зашифрованное тело), так что пуш-сервис может догадаться,
  что это был звонок, но не от кого.
- **Сервер** — адрес и ключи подписки (по адресу видно, чей браузер) и значение `notify`: отличает
  сообщение от квитанции и от звонка. Связи между ящиками это не добавляет: они и так принадлежат
  одному ключу `AUTH`.

Адрес подписки присылает клиент, а запрос по нему делает сервер, поэтому принимаются только
HTTPS-адреса известных пуш-сервисов (`TM_PUSH_HOSTS`), без перенаправлений. На ответ 404 или 410
сервер удаляет подписку; она же удаляется по `push-unsub` и когда у ключа не осталось ящиков.

Настройки сервера: `TM_PUSH_SUBJECT` — контакт владельца для пуш-сервисов (`https://...` или
`mailto:...`); пока он не задан, пуши выключены и `ready` приходит без `push`. Ещё: `TM_PUSH_TTL_SEC`,
`TM_PUSH_DELAY_SEC`, `TM_PUSH_OFFLINE_DELAY_SEC`.

## Звонки

Аудиозвонок один на один на WebRTC. Сигналы — обычные зашифрованные сообщения (`call-*`), поэтому
сервер не знает, что идёт звонок, и не видит адресов. Звук шифрует сам WebRTC (DTLS-SRTP); отпечаток
его ключа записан в `sdp`, а `sdp` пришёл по сквозному каналу — значит, подменить собеседника
посередине нельзя.

```
A → B   call-offer  {call: <id>, sdp}       notify: "call", ttl 60 с
B → A   call-answer {call, sdp}             ttl 60 с
A ⇄ B   call-ice    {call, candidates}      адреса, найденные после отправки sdp; ttl 60 с
A ⇄ B   call-end    {call, reason}          hangup | decline | busy | timeout | failed
```

- `call` — случайный id звонка (16 байт base64url). Сигналы с другим id игнорируются.
- Перед отправкой `sdp` клиент ждёт до 2,5 с, пока браузер соберёт адреса, — обычно всё уходит
  одним сообщением, `call-ice` нужен редко.
- Сигналы живут на сервере 60 секунд (`ttl`): опоздавшее приглашение не должно звонить через час.
  Исключение — `call-end` от звонившего, если на звонок не ответили (`timeout` или `hangup`): он
  хранится как обычное сообщение, и по нему получатель, вернувшись в сеть, узнаёт о пропущенном.
  Такой `call-end` уходит с `notify: "call-end"` — телефон заменит «Входящий звонок» на «Пропущенный».
- Вызов ждёт ответа 45 с. Если оба позвонили друг другу одновременно, остаётся звонок с меньшим
  id: звонивший с бо́льшим молча бросает свой и принимает чужой.
- Занят другим звонком — отвечает `call-end {reason: "busy"}`.
- Запись о звонке в ленте чата каждый клиент ведёт сам (сообщение типа `call` в своей базе,
  собеседнику не отправляется).

**Адреса и IP.** Перед звонком клиент спрашивает у сервера `ice` и получает список для
`RTCPeerConnection`:

```json
{ "t": "ice", "ttl": 21600, "servers": [
  { "urls": ["stun:chat.example:3478"] },
  { "urls": ["turn:chat.example:3478?transport=udp"], "username": "1731400000", "credential": "<base64>" } ] }
```

Логин TURN временный (схема REST API coturn): `username` — время, до которого он годен,
`credential = base64(HMAC-SHA1(секрет, username))`. Выдаётся только ключу `AUTH`, у которого есть
хотя бы один ящик. Список пуст, если TURN не настроен, — тогда соединиться можно только напрямую.

По умолчанию клиент ставит `iceTransportPolicy: "relay"`: звук идёт только через TURN, и собеседник
не узнаёт IP-адрес. TURN-сервер при этом видит адреса обоих и объём трафика, но не содержимое.
Прямое соединение (быстрее, но адрес виден собеседнику) включается в настройках; без TURN оно
используется всегда.

Настройки сервера: `TM_ICE_URLS` (адреса через запятую), `TM_TURN_SECRET` (общий секрет с coturn,
`static-auth-secret`), `TM_TURN_TTL_SEC`. Установка coturn — `deploy/calls-setup.sh`.
