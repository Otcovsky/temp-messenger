# Протокол Temp Messenger, версия 1

## Идентичность

При первом запуске браузер создаёт и хранит в IndexedDB (закрытые ключи неизвлекаемые):

| Ключ | Алгоритм | Назначение |
|---|---|---|
| `IK` | X25519 | ключ личности, обмен ключами |
| `SIG` | Ed25519 | подписи (зарезервирован для групп) |
| `AUTH` | Ed25519 | доступ к своим ящикам на сервере, не связан с личностью |

Если браузер не поддерживает X25519/Ed25519 в Web Crypto, используется `@noble/curves`; закрытые ключи
тогда хранятся как сырые 32 байта. Формат ключей и вычисления те же, так что такие клиенты совместимы с остальными.

## Почтовые ящики

Ящик — случайный ID, 16 байт в base64url (22 символа). Каждому собеседнику выдаётся свой ящик.
Читать ящик может только владелец `AUTH`-ключа, создавший его. Писать может любой, кто знает ID.

## Приглашение

Ссылка `https://<host>/#i=<base64url(JSON)>`. Часть после `#` на сервер не отправляется.

```json
{ "v": 1, "ik": "<IK_A>", "sk": "<SIG_A>", "e": "<E_A>", "m": "<ящик A>", "n": "Имя" }
```

`E_A` — одноразовый X25519-ключ. Принявший (B) создаёт `EK_B` и считает:

```
SK = HKDF-SHA256(ikm = 0xFF*32 || DH(IK_B, E_A) || DH(EK_B, IK_A) || DH(EK_B, E_A),
                 salt = 0*32, info = "TM-X3DH-v1", 32 байта)
AD = IK_B || IK_A
```

B запускает Double Ratchet как отправитель, `E_A` — первый ratchet-ключ A. Первое сообщение B (`hello`)
уходит в ящик A и содержит ящик B. Пока A не ответит, B прикладывает к каждому сообщению заголовок
`pk = {ik: Enc(IK_B), ek: EK_B, e: E_A}`, чтобы A мог вычислить `SK`.

Заголовок `pk` видит сервер, а `IK_B` у человека один на все чаты, поэтому он зашифрован:

```
key (32) || iv (12) = HKDF-SHA256(ikm = DH(EK_B, E_A), salt = 0*32, info = "TM-PreKey-v1")
Enc(IK_B) = AES-256-GCM(key, iv, IK_B, AD = EK_B || E_A)        48 байт
```

`EK_B` одноразовый, этим ключом шифруется одно значение, так что постоянный IV безопасен.
Если `pk.ik` — 32 байта, это открытый `IK_B` от старого клиента; он принимается как есть.

## Double Ratchet

По [спецификации Signal](https://signal.org/docs/specifications/doubleratchet/):

- `KDF_RK(rk, dh) = HKDF(salt = rk, ikm = dh, info = "TM-Ratchet") → rk' (32) || ck (32)`
- `KDF_CK(ck)`: `mk = HMAC(ck, 0x01)`, `ck' = HMAC(ck, 0x02)`
- Шифр: `HKDF(mk, info = "TM-MsgKeys") → ключ AES-256-GCM (32) || IV (12)`, AD = `AD || dh || pn || n`
- До 1000 пропущенных ключей за шаг, хранится не больше 2000.

## Слои сообщения

**1. Конверт, его видит сервер:**
```json
{ "t": "send", "id": "<id>", "to": ["<ящик>"], "payload": "<строка>" }
```

**2. payload:**
```json
{ "v": 1, "h": { "dh": "...", "pn": 0, "n": 3 }, "ct": "<base64url>", "pk": { ... } }
```

**3. Содержимое (внутри `ct`).** JSON, дополненный до кратного 256 байт (0x80, затем нули):
```json
{ "id": "<id>", "ts": 1731312000000, "conv": "<id группы, если есть>", "type": "text", "body": { "text": "..." } }
```

| type | body | |
|---|---|---|
| `hello` | `{name, mailbox, sigPub}` | первое сообщение по приглашению |
| `text` | `{text}` | |
| `file` | `{blob, key, size, name, mime}` | файл, см. «Файлы» |
| `receipt` | `{status: "delivered" \| "read", ids: [...]}` | квитанции |
| `goodbye` | `{}` | собеседник удалил чат |

Неизвестные типы игнорируются. Планируются: `call-*`, `group-*`, `sender-key`, `edit`, `delete`, `reaction`.

## Файлы

Файл передаётся отдельно от сообщения: размер сообщения ограничен 64 КБ.

1. Отправитель создаёт случайный ключ `K` (32 байта) и id файла (16 байт, base64url).
2. Дополняет файл по схеме [Padmé](https://lbarman.ch/blog/padme/) (0x80, затем нули) и шифрует:
   ```
   ct = AES-256-GCM(K, iv = 0*12, padded, AD = "TM-File-v1")
   ```
   Ключ одноразовый, поэтому нулевой IV безопасен, а шифротекст для того же `K` всегда одинаковый —
   повторная загрузка после сбоя отдаёт серверу те же байты.
3. Загружает `ct` на сервер (`PUT /blob/<id>`), затем отправляет обычное сообщение `file`:
   ```json
   { "type": "file", "body": { "blob": "<id>", "key": "<K>", "size": 70000, "name": "отчёт.pdf", "mime": "application/pdf" } }
   ```
4. Получатель скачивает `ct` (`GET /blob/<id>`), расшифровывает, сверяет размер и сообщает серверу,
   что файл скачан (`POST /blob/<id>/done`).

Сервер видит только id, примерный размер и ключ доступа загрузившего (для квоты); имя, тип и ключ
файла — внутри зашифрованного сообщения. Файл стирается, когда его скачали все `n` получателей,
или через 7 дней. Для группы файл загружается один раз с `n` = числу участников, а ключ рассылается
каждому в его сообщении.

```
PUT  /blob/<id>?n=<получателей>   X-TM-Auth: <AUTH pub>.<sig>      тело — ct
     sig = Ed25519(AUTH, "tm-blob-v1:<id>:<длина ct>:<n>")
     201 — сохранён, 200 — уже был (повтор), 403 — подпись, 409 — id занят,
     413 — больше 26 МиБ, 507 — кончилась квота
GET  /blob/<id>                   200 — ct, 404 — нет (истёк или все скачали)
POST /blob/<id>/done              204
```

Клиент отправляет файлы до 25 МиБ. Квоты сервера: 256 МиБ на ключ доступа, 2 ГиБ всего
(переменные `TM_MAX_BLOB_BYTES`, `TM_BLOB_QUOTA_PER_OWNER`, `TM_BLOB_QUOTA_TOTAL`, `TM_BLOB_TTL_SEC`).

## WebSocket `/ws`

```
← challenge {nonce}
→ auth {pub, sig}                 sig = Ed25519(AUTH, "tm-auth-v1:" || nonce)
← ready
→ register {mailbox, invite?}     ← registered {mailbox, created}, затем msg из очереди
                                  invite: true — ящик ждёт ответа на приглашение, false — обычный
→ probe {mailbox}                 ← probe {mailbox, state: "open" | "used" | "none"}
→ unregister {mailbox}            ← unregistered {mailbox}
→ send {id, to:[...], payload}    ← sent {id, failed:[{to, reason}]}
← msg {id, mailbox, payload, ts}
→ ack {mailbox, ids:[...]}        сервер удаляет сообщения
→ ping                            ← pong
← error {code, ref?}                ref — id сообщения (send) или ящик (register, probe, unregister, ack)
```

Перед принятием приглашения клиент спрашивает `probe`: чат создаётся, только если `state = "open"`.
`used` — по ссылке уже подключились (пригласивший перерегистрировал ящик с `invite: false`),
`none` — приглашение отозвано, чат удалён или ящик истёк.

Клиент шлёт `ack`, только когда сообщение и новое состояние храповика записаны в базу одной
транзакцией (или сообщение негодное и отброшено). При сбое записи `ack` не уходит, и сервер
пришлёт сообщение снова при следующей регистрации ящика.

Если сервер ответил на `send` отказом `no_mailbox`, собеседник помечается недоступным. Пометка
снимается, когда от него приходит новое сообщение: ящик мог истечь, пока человек был не в сети.
После `goodbye` пометка окончательная.

Сервер отбрасывает дубликаты по паре (ящик, id), поэтому повторная отправка безопасна.
Недоставленные сообщения хранятся 7 дней, ящик без подключений — 30 дней.
